# 技能派生与强制取消流程

状态：默认可用

## 适用

让 A 技能在特定状态触发 B 技能，或允许平砍、技能中强制使用另一技能。

## 只读闭合

1. 确认目标 PVF。
2. 定位角色职业和 skill registry。
3. 解析 A 技能 ID 和 `.skl`。
4. 解析 B 技能 ID 和 `.skl`。
5. 如需解释参数列，先查 knowledge-pack 内置结构化参数事实表取得 `[static data]` / `[level info]` / `[level property]` 的候选列义。
6. 读取目标 `.skl`，核对结构化事实表候选列义对应的实际列数、列顺序和上下文。
7. 查 A 技能 state、substate、动作、NUT 入口和 static data。
8. 查 B 技能 state、substate 和释放条件。
9. 如果涉及 NUT，查询目标脚本入口和 API，不猜函数名。
10. 标出哪些参数是目标 PVF 已确认，哪些只是结构化事实表或辅助索引线索，哪些仍需验证。

## 写入流程

1. 用户明确授权写 PVF。
2. 明确源 PVF 和输出 PVF。
3. 备份源 PVF。
4. 只改目标技能链必需文件。
5. 保存输出 PVF。
6. 重新打开输出 PVF 读回改动文件。
7. 输出变更清单。

## 游戏内验证

- A 技能能正常释放。
- 指定状态下能触发或强制使用 B 技能。
- 非指定状态不乱触发。
- 技能不会卡死、黑屏、崩溃或长期锁状态。
- 联动有伤害或表现要求时，确认命中、伤害、动作和冷却。

## 已验证的 TP 条件派生样本

若设计使用“目标 TP 等级大于 0”作为派生权限门，必须同时闭合 appendage 轮询入口、TP 学习入口、来源技能动作和目标技能状态，并在目标版本验证未学习与已学习两条分支。

该样本可复用的是流程，不是技能数字或全局规则：

1. 先确认现有 `load_state -> passive -> appendage` 入口确实运行，不因同名历史脚本存在就假设已加载。
2. 同时限制职业 / growtype、来源 state 和来源动作；长技能优先只开放明确动作窗口。
3. 读取目标 TP 的实际技能等级作为权限门，不把基础技能等级或说明文本代替 TP 条件。
4. 先启用目标技能命令，再用目标 PVF 已有的输入检测和 `sq_IsUseSkill` 校验冷却、消耗与释放条件。
5. state / substate 参数只沿用目标 PVF 同技能已有写法。
6. 默认显式排除 PVP；若要支持 PVP，必须另开专项。
7. 实机必须成对测试“未点 TP”和“已点 TP”，并检查来源技能清理、重复结算、重复扣除与卡状态。

该样本不证明任意两个技能都能安全互相取消。抓取、吸附、召唤、脱手对象和长演出技能仍需逐技能闭合退出与清理路径。
